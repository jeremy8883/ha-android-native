## 0. TL;DR (read this first)

- **The default dashboard changed in 2026.x.** The old "Overview" (url_path `null`, auto-generated by
  `original-states`) is no longer the default. Now:
  - The default panel is `home` (`src/data/panel.ts`: `DEFAULT_PANEL = HOME_PANEL`). It is a **frontend-only
    panel**. It has no stored Lovelace config: it builds its dashboard on the client with the `home` strategy, using
    settings from `frontend/get_system_data` keys `home` and `security` (`src/panels/home/ha-panel-home.ts`).
  - Core migrates the old `.storage/lovelace` into a normal dashboard with `url_path: "lovelace"`
    (`core: homeassistant/components/lovelace/__init__.py::_async_migrate_default_config`). The frontend only
    shows `/lovelace` if `hass.panels.lovelace.config` exists (`hasLegacyOverviewPanel`). Otherwise
    `ha-panel-lovelace` redirects to `/home`.
- With no stored config, Lovelace no longer generates `original-states`. On `config_not_found` the frontend now
  builds an **empty sections view with one heading card** (`views/default-view.ts`, `views/default-section.ts`).
- At **20260624.6, visibility conditions are evaluated entirely on the client**. The tag's
  `src/mixins/conditional-listener-mixin.ts` calls `setupConditionListeners`, which re-checks `checkConditionsMet`
  on every hass update and adds media-query and timer listeners (`src/common/condition/listeners.ts`).
  **[main only]**: core conditions in `visibility` are evaluated on the server through `subscribe_condition`
  (`src/common/controllers/condition-evaluator-controller.ts`), and a failed subscription hides the element.
- Strategies (dashboard, view and section level) are plain TS functions run on the client over registries and
  states. The built-in `home` and `areas` strategies are large and change often. This is the biggest compatibility
  risk (§2).

## 1. WebSocket messages for dashboards

All messages go over the standard HA WS (`{id, type, ...}` → `{id, type:"result", success, result | error:{code,message}}`).

| Purpose | Request | Response / notes | Frontend source |
|---|---|---|---|
| List dashboards | `{type:"lovelace/dashboards/list"}` | `LovelaceDashboard[]` = `{id, url_path, require_admin, show_in_sidebar, icon?, title, mode:"storage"\|"yaml", filename? (yaml)}` | `src/data/lovelace/dashboard.ts::fetchDashboards` |
| Create/update/delete dashboard | `lovelace/dashboards/create` (`url_path, mode:"storage", title, icon?, require_admin, show_in_sidebar`), `.../update` (`dashboard_id`, partial), `.../delete` (`dashboard_id`) | admin only | same file |
| Get config | `{type:"lovelace/config", url_path: string\|null, force: boolean}` | `LovelaceRawConfig` = `LovelaceConfig` (`{views, background?}`) **or** `{strategy:{type,...}}` | `src/data/lovelace/config/types.ts::fetchConfig` |
| Save config | `{type:"lovelace/config/save", url_path, config}` | admin; `config` may be dict or YAML string (core: `probatio.Any(str, dict)`) | `saveConfig` |
| Delete config | `{type:"lovelace/config/delete", url_path}` | | `deleteConfig` |
| Resources | `{type:"lovelace/resources"}` | `LovelaceResource[]` = `{id, type:"css"\|"js"\|"module"\|"html", url}`. Core returns `[]` in safe mode. | `src/data/lovelace/resource.ts::fetchResources` |
| Resource CRUD | `lovelace/resources/create\|update\|delete` (`res_type`, `url`, `resource_id`) | storage resource mode only | same |
| Lovelace info | `{type:"lovelace/info"}` | `{resource_mode:"yaml"\|"storage"}` | same |
| Change notification | `subscribe_events` with `event_type:"lovelace_updated"` | event `data:{url_path}`. Core fires `{"url_path": ...}` only (`core: lovelace/dashboard.py:90`). The frontend type also lists `mode`, which core does not send. | `src/data/lovelace.ts::subscribeLovelaceUpdates` |

**`force`**: the frontend sends `force: true` only on a user-triggered refresh (`config-refresh` event →
`_forceFetchConfig`). For YAML dashboards it makes core re-read the file.

**url_path resolution in core** (`core: lovelace/websocket.py::_handle_errors`):
```
url_path is None → dashboards.get("lovelace") or dashboards.get(None)   # prefer migrated "lovelace" dashboard
else            → dashboards.get(url_path)
missing         → error code "config_not_found", "Unknown config specified: <url_path>"
ConfigNotFound  → error code "config_not_found", "No config found."   (storage dashboard with no saved config, or recovery mode)
HomeAssistantError → code "error"
```
The panel's `url_path` comes from `get_panels`: `PanelInfo{component_name:"lovelace", url_path, config:{mode}, title, icon, require_admin, show_in_sidebar}`
(`src/types.ts`, `core: lovelace/__init__.py::_register_panel`). `ha-panel-lovelace` sends `this.panel.url_path` as is.
The legacy `lovelace` panel, registered by `_async_ensure_default_panel` with **no `config`**, makes the frontend run
`navigate("/home")` (`ha-panel-lovelace.ts::_fetchConfig`: `if (!confMode)`).

**Load flow** (`src/panels/lovelace/ha-panel-lovelace.ts::_fetchConfig`):
1. On first load, fetch resources once (`fetchResources`) and inject them (`loadLovelaceResources`), see §10.
2. `fetchConfig(conn, urlPath, force)`.
3. If `isStrategyDashboard(raw)` (`"strategy" in config`), wait until `hass.entities`, `hass.devices` and
   `hass.areas` are loaded, then `generateLovelaceDashboardStrategy(raw, hass)`.
4. If `err.code === "config_not_found"`: when `urlPath === "lovelace"` and `lovelace/dashboards/list` has no
   such dashboard → `/home`. Otherwise use `{views:[{type:"sections", sections:[{type:"grid", cards:[{type:"heading",
   heading: localize("ui.panel.lovelace.editor.section.default_section_title")}]}]}]}`.
5. `checkLovelaceConfig` (`common/check-lovelace-config.ts`) normalises the config: it drops falsy badges and turns a
   deprecated `section.title` into a leading `{type:"heading"}` card (except for strategy sections). The result is
   deep-frozen.
6. Mode is one of `"storage"`, `"yaml"` or `"generated"`. `lovelace_updated` for this url_path triggers a re-fetch,
   or a toast if the user is editing. For YAML mode, the next event after a self-triggered fetch is ignored for 2 s.
   The frontend also re-fetches on WS reconnect (`connection-status` = `connected`).
7. For strategy dashboards, the frontend regenerates with a 200 ms debounce when `checkStrategyShouldRegenerate` is
   true (registry objects replaced) or when `hass.config.state` changes to `RUNNING`.

## 2. Storage vs YAML vs generated, and strategies

### 2.1 Config kinds
- **storage**: `.storage/lovelace.<url_path>`. Saved with `lovelace/config/save`.
- **yaml**: `mode:"yaml"` dashboards declared in `configuration.yaml`. Legacy YAML mode for the default dashboard is
  deprecated ("Remove in 2026.8"): core synthesises a yaml dashboard with `url_path "lovelace"`.
- **strategy** dashboard: the stored config is just `{strategy:{type:"<builtin>"|"custom:<name>", ...options}}`.
  Core auto-creates `map` (`{"strategy":{"type":"map"}}`, `core: lovelace/__init__.py::_create_map_dashboard`).
  New dashboards created from the picker can be `original-states`, `areas`, `home`, `map`, `iframe` or `energy`
  (`src/data/lovelace/config/strategy.ts::LOVELACE_BUILTIN_DASHBOARD_STRATEGY_TYPES`).
- **strategy views/sections**: any view `{strategy:{...}, title?, path?, icon?, subview?...}` (`isStrategyView`) and any
  section `{strategy:{...}, column_span?, visibility?...}` (`isStrategySection`) can appear inside a normal config.
  Each is resolved lazily when that view or section is rendered (`views/hui-view.ts`, `sections/hui-section.ts`).
  The full expansion is in `expandLovelaceConfigStrategies` (`strategies/get-strategy.ts`).

### 2.2 Resolution (`src/panels/lovelace/strategies/get-strategy.ts`)
- `STRATEGIES` registry:
  - **dashboard**: `original-states`, `map`, `iframe`, `areas`, `home`, `energy`.
  - **view**: `original-states`, `energy-overview`, `energy`, `water`, `gas`, `power`, `map`, `iframe`, `area`,
    `areas-overview`, `home-overview`, `home-media-players`, `home-area`, `home-other-devices`, `light`, `security`,
    `climate`, `maintenance`. The last four also back built-in panels (`src/panels/{light,security,climate,maintenance}`).
  - **section**: `common-controls` (`strategies/usage_prediction/common-controls-section-strategy.ts`).
- The element tag for a built-in strategy is `${type}-${configType}-strategy`. For a custom one it is
  `ll-strategy-${configType}-${name}`, or the legacy `ll-strategy-${name}`. The frontend waits up to 5 s
  (`MAX_WAIT_STRATEGY_LOAD`) for the custom element to be defined.
- Interface (`strategies/types.ts`): `static generate(config, hass): Promise<LovelaceConfig|ViewConfig|SectionConfig>`,
  plus optional `shouldRegenerate(config, oldHass, newHass)` and `registryDependencies` (subset of
  `entities|devices|areas|floors|labels|panels`). The default dependency list is entities, devices, areas and floors.
- Legacy custom strategies expose `generateDashboard({config, hass})` or `generateView({view, config, hass})`.
  `cleanLegacyStrategyConfig` flattens `{type, options:{...}}` to `{type, ...options}`.
- Output is merged: `{...configMinusStrategy, ...generated}`. Errors render as a markdown card,
  `"Error loading the dashboard strategy:\n> <err>"`.

**Assessment:** porting `map`, `iframe` and `original-states` is feasible (pure functions over registries, roughly
one week). The `home` and `areas` strategies are **frontend product code that changes nearly every release**. They
use new card types (`home-summary`, `shortcut`, `discovered-devices`, `repairs`, `updates`, `area` with features)
and new WS calls. A Kotlin port would keep drifting from upstream. Recommendation: port `original-states`, `map`
and `iframe`. Route `home`, `areas`, energy and `custom:` strategies to the WebView fallback until they stabilise.
Also note that `/home` is now the default landing page, so most fresh installs land on the hardest case first.

## 3. Data structures

### 3.1 Dashboard and view (`src/data/lovelace/config/types.ts`, `view.ts`)
```ts
LovelaceConfig { views: LovelaceViewRawConfig[]; background?: string | LovelaceViewBackgroundConfig }
LovelaceDashboardStrategyConfig { strategy: {type: string, [k]: any} }
LovelaceBaseViewConfig {
  index?, title?, path?, icon?, show_icon_and_title?, theme?, panel?(legacy → panel view),
  background?: string | {image?: string|MediaSelectorValue, opacity?, size?:"auto"|"cover"|"contain",
                         alignment?: "top left".."bottom right", repeat?, attachment?:"scroll"|"fixed"},
  visible?: boolean | {user?: string}[], subview?, back_path?,
  max_columns?, dense_section_placement?, top_margin?            // sections view only
}
LovelaceViewConfig extends Base { type?, badges?: (string|Partial<LovelaceBadgeConfig>)[], cards?, sections?,
  header?: {card?, layout?:"start"|"center"|"responsive", badges_position?:"bottom"|"top", badges_wrap?:"wrap"|"scroll"},
  footer?: {card?, max_width? (default 600)},
  sidebar?: {sections?: LovelaceSectionConfig[], content_label?, sidebar_label?, visibility?} }   // new, sections view
```
- `computeViewTitle(view, i) = view.title ?? (view.path ? titleCase(view.path) : String(i))`; default icon `mdi:view-compact`.
- **View type** (`views/get-view-type.ts::getViewType`): `type` if set, else `panel:true` → `panel`, else `sections`
  present → `sections`, else `cards` present → `masonry`, else **`sections`**. Built-in layouts:
  `masonry` (always loaded), `panel`, `sidebar`, `sections` (`create-element/create-view-element.ts`). Any other type
  becomes the custom element `hui-${type}-view`, and a `custom:` prefix becomes a raw custom element (§10).
- **visible** (`hui-root.ts::_isVisible`): visible if editing, if `undefined` or `true`, or if an array entry has
  `user === hass.user.id`. Hidden views lose their tab. If the selected view is invisible, the frontend navigates to
  `views.findIndex(_isVisible)`.
- **subview**: no tab is shown. The back button goes to `back_path` (after `sanitizeNavigationPath`), else
  `history.back` (`goBack`), else the dashboard root (`hui-root.ts::_goBack`, `_backPath`).
- **Routing**: `/<dashboard_url_path>/<view.path || index>`. The frontend matches `views[i].path === segment` or the
  numeric index (`hui-root.ts` ~l.770-805).
- **theme**: `applyThemesOnElement` on the view, using `frontend/get_themes` (subscribed; event `themes_updated`).
  Sections and some cards (markdown, entities) also accept `theme`.
- **background**: view background, else dashboard-level `config.background` (`hui-root.ts:460`,
  `views/hui-view-background.ts`).

### 3.2 Sections (`section.ts`)
```ts
LovelaceSectionConfig { type?: string (default "grid"), cards?, visibility?, disabled?, column_span? (default 1),
  row_span?, background?: boolean | {color?, opacity? (default 50)}, title?(deprecated), theme? }
```
Only the `grid` section type is built in (`create-section-element.ts`, `sections/const.ts`). Others become
`hui-<type>-section` custom elements.

### 3.3 Cards, badges
```ts

  grid_options?: LovelaceGridOptions; layout_options?(deprecated); view_layout?: any; [k: string]: any }
LovelaceGridOptions { columns?: number|"full"; rows?: number|"auto"; min_columns?; max_columns?; min_rows?; max_rows? }
LovelaceLayoutOptions (legacy) { grid_columns, grid_rows, grid_min_columns, ... }  // migrateLayoutToGridOptions: ×3 on columns
```

`ensureBadgeConfig` (`badge.ts`): a string becomes `{type:"entity", entity, show_name:true}`, and an object without
`type` becomes `{type:"entity", ...cfg}`.

### 3.4 Masonry columns (`views/hui-masonry-view.ts`)
- Columns = number of matching `min-width` media queries at 300, 600, 900 and 1200 px. Subtract 1 if
  `!narrow && hass.dockedSidebar === "docked"`, with a minimum of 1. A native app has no sidebar, so use width
  thresholds only (CSS px = dp).
- The number of columns created is `min(columns, cards.length)`. Each card goes, in order, to `getColumnIndex`: the
  **first column with size < 5**, otherwise the column with the smallest total. Then add `cardSize` to that column.
  Empty columns are removed. Columns use `flex: 1 0 0; max-width: 500px` (600px below 600 px), with card margin
  `4px 4px 8px`.
- `computeCardSize` (`common/compute-card-size.ts`): `card.getCardSize()` with a 500 ms timeout, falling back to 1.
  Size units are about 50 px. Per-card values:
  - entities: `(title||headerToggle ? 2 : 0) + max(entities.length, 1)` + header/footer sizes.
  - entity: `2` + footer.
  - button: `(show_icon?4:0)+(show_name?1:0)`.
  - glance: `(title?2:0) + rowHeight*ceil(n/(columns||5))`.
  - light: `5`. thermostat: `7`. gauge: `4`. picture: `5`. picture-entity/picture-glance/media-control: `3`. heading: `1`.
  - tile: `1 + (vertical?1:0) + featureRows`.
  - markdown: `card_size ?? round(lines/2) + (title?1:0)`.
  - history-graph: `title ? 2 : 0 + 2*n`. Upstream operator-precedence bug: this returns 2 when a title is set.
  - vertical-stack: sum of children. horizontal-stack: max of children. conditional: size of the inner card.
  - weather: `1 + show_current + show_forecast + (daily?1:0)`.
  - map: `7`, or `1+floor(100*h/w/25)` with an aspect ratio.
  - iframe: `1 + aspect/25` (default 50%).
  - alarm-panel: `4`, or `10` with a numeric keypad.
  - grid: square uses the `SQUARE_ROW_HEIGHTS_BY_COLUMNS` table; otherwise the sum of per-row max sizes.

### 3.5 Sections view (`views/hui-sections-view.ts`)
- CSS tokens: `--column-min-width 320px`, `--column-max-width 500px`, `--column-gap 32px` (8 px when ≤600 px wide),
  `--row-gap 24px`, `--top-margin 80px` (if `top_margin`).
- `columnsController`: `floor((width - padding + gap)/(minColW + gap))`, minimum 1, then clamped to
  `[1, max_columns ?? DEFAULT_MAX_COLUMNS(4)]`. The result is published as `maxColumnsContext`, which the
  `view_columns` condition reads.
- `columnCount = max(1, min(maxColumns, sum(column_span of visible sections) + (editMode?1:0) + (sidebar?1:0)))`.
  When a sidebar exists, content columns = columnCount − 1.
- Sections are placed on a CSS grid: `grid-template-columns: repeat(contentColumnCount, 1fr)`, each with
  `grid-column: span min(column_span, columns)` and `grid-row: span row_span`. `dense_section_placement` sets
  `grid-auto-flow: row dense`, otherwise `row`. The wrapper `max-width` is `columns*500 + (columns-1)*gap`.
- **Sidebar** (new): with one column, the sidebar is stacked below the content, or shown as content/sidebar tabs if
  both `content_label` and `sidebar_label` are set.
- **Section hidden** if `disabled`, if its visibility conditions fail, or if it has at least one card and **all**
  cards are hidden (`hui-section.ts::_updateVisibility`). A hidden section does not count toward column spans.
- Background alignment logic: `views/sections-background-alignment.ts`.

### 3.6 Grid section (`sections/hui-grid-section.ts`, `common/compute-card-grid-size.ts`)
- The section has `12 × column_span` base columns, `--row-height 56px`, `--row-gap 8px`, `--column-gap 8px`.
- Per card: `hui-card.getGridOptions()` = `{...element.getGridOptions(), ...config.grid_options || migrate(layout_options)}`
  (`cards/hui-card.ts`). Then `computeCardGridSize`: defaults `columns:12, rows:"auto"`, clamped by min/max with
  `conditionalClamp`.
- `columns:"full"` spans all columns. A numeric `rows` gives height `rows*(56+8)-8` (`fit-rows`). `"auto"` uses
  intrinsic height. Precise mode is when `columns % 3 != 0`.
- Element defaults:
  - tile `{columns:6, rows:1(+1 vertical)(+featureRows), min_columns: 6 (12 if inline features, 3 if vertical), min_rows: rows}`.
  - heading `{columns:"full", rows:"auto", min_columns:3}`.
  - entities `{columns:12, rows:"auto", min_columns:3}`.
  - button `{rows:2, columns:6, min_columns:2, min_rows:2}` with icon + name/state, else `{1,3}`.
  - Grep `getGridOptions` in `cards/` for the rest.

## 4. Built-in element inventory

How a type is resolved (`create-element/create-element-base.ts::tryCreateLovelaceElement`):
- `custom:x` → custom element `x`.
- Otherwise the tag is `hui-${type}-${suffix}`, where suffix is one of `card`, `badge`, `row`, `element`,
  `header-footer`, `card-feature`, `section`, `view` or `heading-badge`.
- Rows without `type` but with `entity` use `DOMAIN_TO_ELEMENT_TYPE[domain] || "simple"` + `-entity`.
- Unknown type → error card `Unknown type encountered: <type>`.
- Missing custom element → hidden error card, shown after 2 s, rebuilt via `ll-rebuild` when the element is defined.

## 5. Conditions and visibility

Types (`src/panels/lovelace/common/validate-condition.ts`):
- `Condition`: `view_columns{min,max}`, `location{locations[]}`, `numeric_state{entity?,attribute?,above?,below?}`,
  `state{entity?,attribute?,state?,state_not?}`, `screen{media_query}`,
  `time{after?,before?,weekdays?: "mon".."sun"}`, `user{users[]}`, `and|or|not{conditions}`.
- `LegacyCondition`: `{entity, state|state_not}` with no `condition` key (old conditional card).
- `VisibilityCondition` also allows **core automation conditions**: core `state`/`numeric_state` (with `entity_id`),
  `sun`, `zone`, `template`, `device` and integration platform conditions. Logical `conditions` may be a single item
  or a list.
- Visibility applies to: cards (`visibility` in `hui-card`), sections, badges, heading badges, and `view.sidebar`.
  The conditional card (`conditions:`), conditional row and conditional element use the same machinery. Views have
  no `visibility`, only `visible`.
- `disabled: true` hides cards and sections unconditionally (outside edit mode).

**Local semantics** (`checkConditionsMet`), to port exactly:
- **state**: the entity is `condition.entity_id || condition.entity || context.entity_id`. The "host entity"
  (`getConfigEntityId(cardConfig)`) is folded in by `addEntityToCondition`. With an attribute, the value is
  `String(attr)` or `"unknown"`. A missing entity gives `"unknown"`.
  - Each `state` value that is an existing entity ID is expanded to that entity's state.
  - `state` → match is `includes`; `state_not` → match is `!includes`. If neither is set → `false`.
- **numeric_state**: `above`/`below` strings may be entity IDs (replaced by their state). The check is
  `above < value < below` (strict). A `NaN` state → false. A `NaN` bound is ignored.
- **screen**: `matchMedia(media_query)`. A native port has to evaluate CSS media queries such as
  `(min-width: 1024px)` against dp width. Plan a small media-query parser.
- **user**: `users.includes(hass.user.id)`.
- **location**: the state of the current user's `person` entity (`getUserPerson`) is in `locations`
  (zone names / `home` / `not_home`).
- **time**: `checkTimeInRange` (`common/datetime/check_time.ts`). Uses the server timezone if
  `locale.time_zone === "server"`. Handles ranges that cross midnight.
- **view_columns**: compares against `context.max_columns` (sections view column count). If unset → true.
- **and**: all. **or**: some. **not**: `!all(children)` (NOT of AND). An empty `conditions` → true.

**At 20260624.6 there is no server evaluation.** The tag only has the lovelace condition types listed above,
evaluated locally in `checkConditionsMet`. `screen` and `time` conditions get re-evaluation listeners from
`common/condition/listeners.ts` (`setupMediaQueryListeners`, `setupTimeListeners`, with
`calculateNextTimeUpdate`). The block below describes `main` only.

**[main only] Server evaluation** (`src/common/condition/{translate,split,evaluate-locally,listeners}.ts`,
`src/common/controllers/condition-evaluator-controller.ts`, `src/mixins/conditional-listener-mixin.ts`):
- Client-only types: `screen`, `user`, `view_columns`, `location`, `time`.
- All other leaves are "server" unless they have legacy-only semantics (an attribute on a lovelace state condition,
  entity-ID comparison values, entity-ID numeric bounds). Those stay local.
- The tree is split (`splitConditionTree`). Each maximal server subtree is translated
  (`translateToCoreCondition`: lovelace `entity` → `entity_id`, incomplete → `not(and[])`) and subscribed:
  - request: `{type:"subscribe_condition", condition: <core condition>}`
  - events: `{result: boolean, template_errors?: string[]}` or `{error: string}`
  - core handler: `core: websocket_api/commands.py::handle_subscribe_condition`. Validation failure →
    `invalid_format`.
- Three-valued AND/OR combine client and server results. Before the server replies, a local seed is used for
  state/numeric_state leaves whose entity exists. Unknown → hidden.
- **Any subscription error → hidden**, including `unknown_command` on cores that predate `subscribe_condition`.
- Native recommendation: implement the same split. Evaluate the client and legacy leaves locally, and keep one
  `subscribe_condition` per server subtree. On older cores, fall back to local evaluation of `state` and
  `numeric_state` instead of hiding.

## 6. Actions

Types (`src/data/lovelace/config/action.ts`):
- `more-info{entity?}`, `toggle`, `call-service|perform-action{perform_action, service(deprecated), target?, data?, service_data(deprecated)}`
- `navigate{navigation_path, navigation_replace?}`, `url{url_path}`, `assist{pipeline_id?, start_listening?}`
- `none`, `fire-dom-event` (any extra keys)
- All accept `confirmation?: {text?, title?, confirm_text?, dismiss_text?, exemptions?: {user}[]}`.
  A bare `confirmation: true` is also used in practice: it is truthy and gets the default text.

`handleAction(node, hass, config, "tap"|"hold"|"double_tap")` (`common/handle-action.ts`):
1. Pick `config.<action>_action`. If it is absent → **`{action:"more-info"}`**. This is the global default, but most
   cards inject their own defaults in `setConfig`.
2. Confirmation: skipped if the current user ID is in `exemptions`. Otherwise show a dialog whose default text is
   `ui.panel.lovelace.cards.actions.action_confirmation` with
   `action = "<Domain name>: <service name>"`. The service name comes from `frontend/get_translations` categories
   `title` and `services`, then `hass.services[d][s].name`.
3. Dispatch:
   - `more-info`: `actionConfig.entity || config.entity || camera_image || image_entity`, else a toast.
   - `navigate`: in-app route.
   - `url`: `window.open(sanitizeUrl(url_path))`.
   - `toggle`: `toggleEntity`, i.e. `turnOnOffEntity(!STATES_OFF.includes(state))`. `STATES_OFF = closed, locked, off`.
     The service comes from `SPECIAL_TOGGLE_ACTIONS` (`common/entity/get_toggle_action.ts`):
     button/input_button → `press`, cover → `open_cover`/`close_cover`, lock → `unlock`/`lock`,
     valve → `open_valve`/`close_valve`, scene → `turn_on`, group → domain `homeassistant`, otherwise
     `turn_on`/`turn_off`.
   - `perform-action`: `call_service` with `data ?? service_data` and `target`.
   - `assist`: voice dialog, `pipeline_id` default `"last_used"`.
   - `fire-dom-event`: `ll-custom` DOM event. Custom cards and browser_mod use it. A native app can only forward it
     to a WebView.
   - `none`: nothing.
4. Haptics are forwarded via `forwardHaptic` (light, warning, failure).

Gestures (`common/directives/action-handler-directive.ts`): hold = 500 ms, double-tap window = 250 ms. Double-tap
detection is only armed if `hasDoubleClick` (`hasAction(double_tap_action)`, i.e. defined and not `none`). Otherwise
taps fire immediately.

Defaults per card (from each `setConfig`):
- **tile**: `tap: more-info`. `icon_tap`: `toggle` if the domain is in `DOMAINS_TOGGLE` (fan, input_boolean,
  light, switch, group, automation, humidifier, valve) or is button, input_button or scene; else `none`.
- **button**: `tap: toggle` if in `DOMAINS_TOGGLE`, else `more-info`; `hold: more-info`; `double_tap: none`.
- **light**: `tap: toggle`, `hold: more-info`.
- **picture-glance**: per entity, `tap: more-info` (dialog) or `toggle`; `hold: more-info`.
- **picture-entity**: `tap: more-info`.
- **picture**: `more-info` if it has an entity, else `none`.
- **glance**: `hold: more-info`.
- **button/buttons rows**: `hold: more-info`.
- **heading badges**: all `none`.
- **entity badge, entity card, generic rows**: rely on the `more-info` fallback.

## 8. Entity state and registry subscriptions

The frontend uses `subscribeEntities` from home-assistant-js-websocket (`src/state/connection-mixin.ts:269`,
pre-warmed in `src/entrypoints/core.ts`). On the wire:

```
→ {"id":N,"type":"subscribe_entities", "entity_ids"?: [...], include/exclude filter?}
← {"id":N,"type":"result","success":true,"result":null}
← {"id":N,"type":"event","event":{"a":{ "<entity_id>": CompressedState, ... }}}      // initial full snapshot
← {"id":N,"type":"event","event":{"a":{...}}|{"c":{...}}|{"r":[...]}}               // later, one per state_changed
CompressedState = {"s": state, "a": attributes, "c": context_id | {"id","parent_id","user_id"}, "lc": last_changed_ts(float s), "lu"?: last_updated_ts (omitted if == lc)}
Diff ("c" map value) = {"+": {"s"?, "lc"?, "lu"?, "c"?: id | {parent_id?, user_id?, id?}, "a"?: {changed attrs}}, "-"?: {"a": [removed attr names]}}
```
- Source: `core: websocket_api/messages.py::_state_diff_event` (keys `ENTITY_EVENT_ADD "a"`, `REMOVE "r"`,
  `CHANGE "c"`; `STATE_DIFF_ADDITIONS "+"`, `STATE_DIFF_REMOVALS "-"`), `core: core.py::State.as_compressed_state`,
  `commands.py::handle_subscribe_entities`.
- If `lc` changes, `lu` is not sent and the client sets `last_updated = last_changed`. If only `lu` changes, `lu` is
  sent. When `+.c` is a string it replaces the context id only.
- Client decoding (hajs `entities.ts`, behaviour known from 9.x):
  - add: build `HassEntity{entity_id, state:s, attributes:a, context: typeof c==="string" ? {id:c, parent_id:null, user_id:null} : c, last_changed: ISO(lc*1000), last_updated: ISO((lu??lc)*1000)}`.
  - change: merge `+` (attributes merged), delete the attributes in `-.a`.
  - remove: delete.
  - Timestamps are float epoch seconds and must be converted to ISO strings or `Instant`.
- Entity visibility is filtered by user permissions on the server.

Registries (`src/state/connection-mixin.ts::hassConnected`). All are re-fetched (debounced 500 ms for the entity
registry) when their event fires:

| hass field | fetch | event |
|---|---|---|
| `entities` | `config/entity_registry/list_for_display` → `{entities:[{ei, di?, ai?, np? ([main only]), lb[], ec?(index), en?, ic?, pl, tk?, hb?, dp?, hn?}], entity_categories:{idx: "config"\|"diagnostic"}}`. Decoded to `EntityRegistryDisplayEntry{entity_id, device_id, area_id, next_name_part, labels, entity_category, translation_key, platform, name, icon, hidden, display_precision, has_entity_name}` (`src/data/entity/entity_registry.ts`, `src/data/ws-entity_registry_display.ts`) | `entity_registry_updated` |

## 10. Custom cards, resources and the WebView fallback

- Resources (`common/load-resources.ts`): each URL is resolved against `hassUrl`. Then:
  - `css` → `<link>` (cached)
  - `js` → `<script>` (cached)
  - `module` → `<script type=module>`
  - `html` → warns "Unknown resource type" (not loaded any more)
- They are loaded **once per page load**, in parallel with the config fetch. Cards are created before the custom
  elements are defined and are upgraded later via `customElements.whenDefined` → `ll-rebuild`, with a 2 s error-card
  delay.
- Additional JS can come from `frontend: extra_module_url` / `extra_js_url_es5` (HACS uses `add_extra_js_url`).
  These are injected into the **server-rendered `index.html`** (`core: frontend/__init__.py`), with a newer
  `frontend/subscribe_extra_js` WS. They are **not** in `lovelace/resources`.
- Custom types:
  - cards `custom:<tag>` → element `<tag>`
  - badges, rows, card features, header-footers: same mechanism
  - views: `type: custom:<tag>` or a bare `<type>` → `hui-<type>-view`
  - sections: `hui-<type>-section`
  - strategies `custom:<name>` → `ll-strategy-<kind>-<name>`
  - registries for editor/pickers: `window.customCards`, `window.customCardFeatures` (+ deprecated
    `customTileFeatures`), `window.customBadges`, `window.customStrategies` (`src/data/lovelace_custom_cards.ts`,
    `lovelace_custom_strategies.ts`)
- Custom elements depend on the full `hass` object, on internal elements (`ha-card`, `ha-icon`, `ha-state-icon`,
  `hui-generic-entity-row`, `ha-entity-toggle`), on `window.loadCardHelpers()` (`custom-card-helpers.ts` exports
  `createCardElement`, `createRowElement`, `createBadgeElement`, `createHeaderFooterElement`, `createHuiElement`,
  `importMoreInfoControl`, `showConfirmationDialog`, `showEnterCodeDialog`, ...), on DOM events (`hass-more-info`,
  `ll-custom`, `location-changed`, `hass-notification`), and on theme CSS variables.

**Implications for a WebView fallback**
- A per-card WebView cannot host a custom card in isolation, because it needs the HA frontend runtime: `hass`, Lit,
  internal `ha-*` elements and themes. Practical options:
  - (a) A **whole-view or whole-dashboard WebView** loading `/<url_path>/<view>?kiosk-like` from HA's own frontend.
    This is simplest and most robust. Use it whenever a view contains any `custom:` type, an unknown type, a custom
    view/section/strategy, or a P3 card.
  - (b) A per-card WebView of a bundled "card host" page that boots the HA frontend app shell and renders one card
    config. This needs a custom entrypoint and is fragile (internal APIs, auth injection, height measuring).
- Use the existing companion-app external bus (`externalApp`) for auth and haptics in the WebView.
- Decide fallback granularity from a static scan of the config before rendering: walk cards, rows, badges, features,
  `custom:` prefixes, `strategy` keys and unknown types.

## 11. Internal or unstable surfaces we would depend on

None of the following is documented public API. Only the WS command names are semi-stable.
1. **The Lovelace config schema itself.** It is defined only by frontend TS types. New keys keep appearing:
   `sidebar`, `header`/`footer`, `grid_options` (replacing `layout_options`), name arrays, `state_content`,
   `features_position`, heading `badges` (replacing `entities`), `visibility` with core conditions.
2. **Strategy outputs and built-in strategy logic** (`home`, `areas`, `original-states`). These are pure frontend
   code and change every release.
3. **`config/entity_registry/list_for_display`** compressed keys (`ei`, `di`, `hn`, `dp`, ...; `np` on main only).
   These are frontend-private and keep being extended.
4. **Device registry child devices** (stripped entries, `parent_device_id`). New, with frontend-side resolution.
5. **`subscribe_condition`**. New, and the frontend has no version fallback.
6. **`frontend/get_icons` / `frontend/get_translations` resource layouts**: key formats such as
   `component.<d>.entity_component.<dc>.state.<s>` and `range` icons.
7. **Theme and state-color CSS variable names** (`--state-<domain>-...-color`, `color.globals.ts`).
8. **`frontend/*_system_data` keys** `home`, `security`, `core` (`default_panel`, `onboarded_version`).
9. `getCardSize` / `getGridOptions` numbers, and masonry and sections breakpoints. These are layout behaviour, not
   contract.
10. `usage_prediction/common_control`, `energy/*` and repairs/config-flow subscriptions used by the home cards.
11. Legacy YAML default-dashboard behaviour (deprecated, "Remove in 2026.8") and the `url_path: null` → `"lovelace"`
    preference in core.

## 12. The `/home` panel and the `home` strategy (frontend 20260624.6)

This is what the target user sees. Paths below are in `~/projects/ha-refs/frontend-20260624.6`.

### 12.1 How the user gets here
- In core, `_async_ensure_default_panel` registers the `lovelace` panel **without `config`** when no `lovelace`
  dashboard exists.
- `ha-panel-lovelace.ts::_fetchConfig` sees `!this.panel.config?.mode` and calls `navigate("/home", {replace:true})`

  registered by core frontend (`core: frontend/__init__.py`, around l.620). Its sub-routes are

### 12.5 Section strategy `common-controls` (`strategies/usage_prediction/common-controls-section-strategy.ts`)
- Output is a grid section. It starts with `config.heading`, or a legacy `title`/`icon` heading.
- If `include_entities.length >= limit`, it uses the first `limit` favorites and **makes no WS call**.
- If `usage_prediction` is not in `hass.config.components`, it emits a markdown card with
  `strategy.common_controls.not_loaded`, and the section gets `disabled = hide_empty`.

  (`src/data/usage_prediction.ts`; `core: usage_prediction/common_control.py`). The result is filtered to entities

  record the WS response.

### 12.10 Portability to a pure Kotlin function
- The four view generators plus the dashboard and section strategies come to about 1,600 LOC of TS. The helpers
  add about 400 LOC (entity_filter, context, hierarchy, area tile, feature predicates, shortcuts, summaries).
- All of it is **deterministic data transformation over `(states, entities, devices, areas, floors, panels,
  config.components, user.is_admin, homeSystemData, localize)`** plus two awaited WS results: `energy/get_prefs`
  and `usage_prediction/common_control`.
- There is no DOM or layout dependency. `view_columns` conditions are emitted as data, not evaluated.
- Estimate: **3-5 days** for a faithful Kotlin port with JSON-equivalent output, e.g.
  `suspend fun generateHome(input: HomeInputs, ws: HomeWs): LovelaceConfig`, emitting `JsonObject` trees so the
  same renderer handles stored and generated configs.
- Pitfalls:
  - **JS object key order.** `Object.values(hass.areas)` / `Object.keys(hass.states)` follow insertion order. That
    is the order of the WS list response, except that integer-like keys sort first numerically. Area IDs are
    slugs, so this is rarely an issue, but mirror it with `LinkedHashMap` built in WS order.
  - `computeStateName` / `stripPrefixFromEntityName` semantics, and `floorDefaultIcon`.
  - `localize` placeholder interpolation (`{user}` → `{{ user }}`).
- **Drift**: between tag 20260624.6 and main (about 3.5 months), `home-overview-view-strategy.ts` changed in
  **412 diff lines**: security alerts, favorites helper, climate check, regeneration rules. home-area changed in 83,
  media-players in 36, other-devices in 23. Budget about 1-2 days per HA release to re-sync, and **pin the port to
  the server's frontend version**. `frontend/get_system_data` does not report it; read the version from
  `hass.config.version` and keep a version→behaviour table.

### 12.11 Running the upstream TS headless for differential testing
The `generate()` functions are `static async` methods on Lit `ReactiveElement` subclasses decorated with
`@customElement`. Importing them evaluates `customElements.define`, and the transitive imports pull in Lit
components (`card-features/*` import `ha-control-slider` and others) and CSS. So:
- **Node option**: bundle the strategy entry modules with esbuild/rollup using the repo's build defines
  (`__DEV__`, `__DEMO__`, `__BACKWARDS_COMPAT__`, `__HASS_URL__`, etc. from `build-scripts/`). Run under a DOM shim
  (`happy-dom` or `@lit-labs/ssr-dom-shim` for `customElements`/`HTMLElement`). Then call
  `customElements.get("home-overview-view-strategy").generate(cfg, fakeHass)`.
  - Effort: about 1-2 days to get the import graph to load. Expect a few stubbed modules: workers, `marked`,
    anything touching `window.matchMedia` or `getComputedStyle` at import.
- **Fake `hass`** (only these fields are read by the home strategies):
  - `states` (HassEntity map; only `entity_id`, `state`, `attributes.{device_class, supported_features, supported_color_modes, friendly_name}`, ...)
  - `entities` (display-registry decoded shape, §8), `devices`, `areas`, `floors`
  - `panels` (keys only)
  - `config.{state, recovery_mode, components}`
  - `user.{is_admin, name}`
  - `localize(key, params)`: a flattened `en.json` lookup with `{x}` interpolation, or identity for key-level diffs
  - `callWS(msg)` returning canned `energy/get_prefs` / `usage_prediction/common_control`
  - All of this is plain JSON and can be recorded from a live server in one go: `get_states`, the four registry
    lists, `get_panels`, `get_config`, `auth/current_user`, plus the two WS replies. Faking it is easy.
- **Lower-effort oracle**: Playwright against the real HA (2026.7.4) frontend. After `/home` loads, the strategy
  elements are registered. In page context, evaluate
  `customElements.get("home-dashboard-strategy").generate(cfg, document.querySelector("home-assistant").hass)` and
  each view strategy, and dump the JSON.
  - This uses the exact shipped bundle and real data, with no build work. Recommended for CI golden files: record
    the fixture and expected JSON from the live page, then assert that the Kotlin output for the same fixture is
    JSON-equal.

## Top compatibility risks

1. **The default landing page is now `/home`, and it is the only dashboard on installs that never saved one.** It is a client-generated `home` strategy with fast-moving,
   home-specific cards and WS calls. Porting it faithfully is costly and will drift. Use WebView first, or a reduced
   native port.
2. **Visibility semantics are moving to the server.** At 20260624.6 visibility is purely client-side (easy to port).
   On main it uses `subscribe_condition` and core conditions (sun, zone, template, device). A newer server will need
   that split, so design the evaluator for both.
3. **Custom cards, `custom:` strategies and HACS `extra_module_url`** cannot be rendered natively. Fallback
   granularity (view vs card) and WebView auth/theming are the main UX risk.
4. **State/name/icon formatting depends on backend translation and icon resources** and on new naming rules
   (`next_name_part`, `EntityNameItem[]`, child devices). Without bit-exact ports, labels will differ from the web UI.
5. **Layout parity.** Sections view grid math, masonry `getCardSize` heuristics, the media-query-driven `screen`
   condition and `view_columns` all assume CSS px widths and must be reproduced exactly for configs to look the same.
6. **Schema churn.** Untyped `[key: string]: any` configs, deprecated aliases (`service`/`service_data`,
   `layout_options`, section `title`, heading `entities`, `display_type`, legacy conditions) and new keys per release
   require lenient parsing that preserves unknown keys and has per-type migrations (`migrate-card-config.ts`,
   `check-lovelace-config.ts`).
7. **Heavy data cards** (history, statistics, energy, map, calendar, todo, camera/WebRTC) each bring their own
   streaming protocol. Defer them to WebView in M1.
